API가 느리다는 이야기가 나오면 캐시가 빠르게 후보에 오릅니다.

Spring을 사용한다면 코드도 간단해 보입니다.

```java
@Cacheable(cacheNames = "items", key = "#id")
public Item findById(Long id) {
    return itemRepository.findById(id)
        .orElseThrow();
}
```

같은 `id`가 다시 들어오면 원본을 조회하지 않고 캐시에 저장한 값을 반환합니다. 느린 조회를 매번 실행하지 않아도 되니 응답 시간과 원본 저장소의 부하를 줄일 수 있습니다.

그렇다면 느린 조회에는 일단 캐시부터 붙이면 될까요?

캐시는 원본 데이터를 복사해두는 공간입니다. 복사본을 만들면 언제 지울지, 얼마나 저장할지, 원본과 값이 달라졌을 때 어떻게 처리할지도 함께 결정해야 합니다.

캐시를 사용할 수 있다는 사실과 캐시를 사용하는 편이 이득이라는 판단은 별개의 문제입니다.

## 느리면 캐시부터?

캐시를 적용하기 전에 먼저 느린 이유를 확인해야 합니다.

불필요한 전체 조회나 빠진 인덱스가 원인이라면 원본 조회부터 고쳐야 합니다. 캐시를 붙여도 Cache Hit 요청만 빨라집니다. Cache Miss에서는 느린 쿼리와 과도한 네트워크 호출이 다시 실행됩니다.

```text
Cache Hit
캐시 조회 → 결과 반환

Cache Miss
캐시 조회 → 원본 조회 → 캐시 저장 → 결과 반환
```

Miss 경로에는 캐시 조회와 저장이 추가됩니다. 원본 조회가 원래 저렴하거나 같은 결과가 거의 재사용되지 않는다면 캐시를 붙인 뒤 오히려 할 일만 늘어날 수 있습니다.

트래픽이 몰릴 때 Cache Miss가 한꺼번에 발생하고 원본 응답을 동기식으로 기다린다면, 느린 호출이 요청 스레드와 커넥션 풀을 소진해 장애로 이어질 수 있습니다.

그래서 캐시 적용 여부는 다음 세 단계로 나눠서 보는 편이 좋습니다.

```text
캐시가 가능한가?
        ↓
캐시가 효과적인가?
        ↓
유지비용보다 이점이 큰가?
```

## 먼저, 캐시할 수 있을까?

가장 먼저 볼 것은 캐시 키입니다.

캐시 키는 어떤 요청의 결과를 다시 사용할지 구분합니다. `itemId`처럼 경우의 수가 제한된 값도 있지만 검색어, 필터, 정렬 조건, 페이지 번호가 모두 키에 들어가면 가능한 조합이 빠르게 늘어납니다.

```text
item:{itemId}

search:{keyword}:{category}:{sort}:{page}:{size}
```

서로 다른 캐시 키의 수를 카디널리티라고 합니다. 카디널리티가 넓다고 무조건 캐시할 수 없는 것은 아닙니다. 다만 새로운 키가 계속 만들어지는데 같은 키를 다시 조회하지 않는다면 캐시 공간만 사용하고 재사용할 기회는 적습니다.

예를 들어 상세 화면의 인기 항목 몇 개는 같은 키로 반복 조회될 가능성이 높습니다. 반면 사용자가 자유롭게 조합하는 검색 조건은 요청마다 다른 키가 만들어질 수 있습니다.

```text
낮은 카디널리티 + 반복 조회
→ 같은 캐시 값을 여러 요청이 재사용

높은 카디널리티 + 일회성 조회
→ 저장한 값을 다시 쓰기 전에 밀려날 수 있음
```

키를 정했다면 원본 데이터가 바뀌는 시점도 알아야 합니다.

## 캐시된 값을 언제 지울 수 있을까?

원본이 바뀌었는데 캐시에는 이전 값이 남아 있다면 Stale Data가 됩니다.

Stale Data란 원본 데이터가 변경되었지만 캐시에는 변경 전 값이 남아 있는 상태를 말합니다.

데이터 변경을 애플리케이션이 모두 알고 있다면 변경이 성공한 뒤 관련 키를 제거할 수 있습니다. 이를 캐시 무효화 또는 Evict라고 합니다.

```text
원본 데이터 변경 성공
        ↓
관련 캐시 키 Evict
        ↓
다음 조회에서 최신 값 적재
```

반대로 다른 시스템이나 배치가 원본을 바꾸는데 변경 시점을 전달받지 못한다면 정확한 Evict 시점을 알기 어렵습니다. 이때는 TTL로 일정 시간이 지나면 값을 만료시키거나, 오래된 값을 어느 정도 허용할지 정해야 합니다.

최신 값만 반환해야 하는 데이터인데 변경 시점도 알 수 없다면 캐시 적용 난도가 크게 올라갑니다. TTL을 짧게 설정하면 오래된 값의 노출 시간은 줄지만 캐시를 재사용할 시간도 함께 줄어듭니다.

```text
TTL이 너무 길다
→ 오래된 값이 남을 가능성 증가

TTL이 너무 짧다
→ Miss와 원본 재조회 증가
```

적절한 Evict 시점을 알 수 있는지, 아니면 허용 가능한 Stale 범위를 정할 수 있는지가 첫 번째 판단 기준입니다.

## 그래서 캐시가 효과가 있을까?

캐시를 만들 수 있다고 바로 효과가 생기는 것은 아닙니다.

캐시가 효과를 내려면 같은 키를 반복해서 조회해야 합니다. 캐시가 비어 있다면 첫 요청은 원본에서 값을 가져와 캐시에 저장해야 합니다. 이후 요청이 같은 키를 찾아야 캐시가 효과를 발휘할 수 있습니다.

이 성질은 Cache Hit Ratio로 확인할 수 있습니다.

```text
Hit Ratio = Cache Hit / (Cache Hit + Cache Miss)
```

하지만 Hit Ratio만 높으면 된다는 뜻은 아닙니다.

원본 조회가 1초 걸리는 작업과 몇 ms 안에 끝나는 작업은 Hit 한 번으로 아끼는 비용이 다릅니다. 반대로 원격 캐시를 사용하면 네트워크 통신과 직렬화 비용이 추가됩니다.

다음 식은 정확한 비용 계산식이 아니라 판단할 항목을 단순화한 것입니다.

```text
캐시의 이점
≈ Hit 횟수 × Hit에서 줄어드는 원본 조회비용

캐시의 비용
≈ 전체 캐시 조회비용 + Miss 처리비용 + 저장·무효화 비용
```

같은 키가 자주 반복되고 원본 조회비용이 클수록 캐시가 유리해집니다. 반대로 키가 대부분 한 번만 조회되거나 원본 조회가 이미 저렴하다면 높은 운영 복잡도를 감수할 이유가 줄어듭니다.

## 그렇다면 캐시 유지비용은?

캐시를 붙이면 관리할 데이터 복사본이 하나 더 생깁니다.

원격 캐시를 사용한다면 메모리와 네트워크, 직렬화 비용도 관리해야 합니다. 캐시가 꽉 찼을 때 어떤 값을 제거할지도 정해야 합니다.

데이터 변경이 너무 빈번하면 상황은 더 복잡해집니다.

```text
조회 → 캐시 저장 → 원본 변경 → Evict
조회 → 캐시 저장 → 원본 변경 → Evict
조회 → 캐시 저장 → 원본 변경 → Evict
```

값을 저장하자마자 지워야 한다면 Hit가 발생할 시간도 짧아집니다. 캐시 적재와 제거만 반복하면서 Hit Ratio는 낮게 나올 수 있습니다.

캐시에 저장해야 할 데이터의 양도 확인해야 합니다. 키의 카디널리티가 넓고 값의 크기까지 크다면 메모리 사용량이 빠르게 늘어납니다. 메모리가 부족해 값이 계속 밀려나면 같은 값을 다시 적재하는 작업이 반복됩니다.

## 왜 예전 값이 반환될까?

Evict 시점을 알고 있어도 경쟁 조건은 남습니다.

Cache-Aside 방식에서는 Cache Miss가 발생하면 원본을 조회한 뒤 그 결과를 캐시에 저장합니다. 이 과정과 데이터 변경이 동시에 실행되면 Evict가 끝난 뒤 이전 값이 다시 저장될 수 있습니다.

```text
요청 A  캐시에 값이 없음
요청 A  변경 전 원본 조회 시작

요청 B  원본 데이터 변경
요청 B  캐시 Evict

요청 A  변경 전 조회 결과 반환
요청 A  이전 값을 캐시에 저장
```

요청 B는 캐시를 지웠지만, 더 일찍 시작한 요청 A가 늦게 끝나면서 변경 전 값을 캐시에 다시 저장했습니다.

이 문제를 다루려면 데이터의 성격에 따라 TTL, 버전 확인, 캐시 갱신 순서, 동시 적재 제어 같은 방법을 검토해야 합니다. 어떤 방식을 선택하더라도 구현과 운영 비용이 추가됩니다.

오래된 값이 잠시 보여도 되는 데이터와 반드시 최신이어야 하는 데이터는 같은 기준으로 캐시할 수 없습니다. Stale Data의 허용 범위를 먼저 정해야 무효화 전략도 정할 수 있습니다.

## 세 가지 질문으로 돌아가면

캐시를 적용하기 전에는 다음 세 묶음으로 질문을 정리할 수 있습니다.

| 구분 | 확인할 질문 |
| --- | --- |
| 캐시가 가능한가? | 키의 카디널리티를 감당할 수 있는가? Evict 시점을 알거나 Stale 범위를 정할 수 있는가? |
| 캐시가 효과적인가? | 같은 키가 반복 조회되는가? 원본 조회비용이 큰가? 충분한 Hit Ratio를 기대할 수 있는가? |
| 유지할 가치가 있는가? | 변경이 너무 빈번하지 않은가? 저장할 데이터가 너무 많지 않은가? 무효화 경쟁 조건을 관리할 수 있는가? |

세 질문에 모두 답할 수 있어야 캐시를 붙일 근거가 생깁니다.

가능하지만 효과가 작다면 적용하지 않는 편이 낫습니다. 효과는 있지만 유지비용이 크다면 캐시할 범위를 줄이는 방법도 검토할 수 있습니다.

## 그래서, 걍 캐쉬 써?

느린 조회에서 캐시는 매력적인 선택입니다. 반복되는 비싼 조회를 줄이는 데 분명한 효과가 있습니다.

하지만 캐시는 느린 코드를 빠르게 바꾸는 마법이 아닙니다. 원본 데이터의 복사본을 하나 더 만들고 그 복사본의 수명과 정합성을 관리하는 선택입니다. Cache Miss가 몰렸을 때 원본 API와 서버가 요청을 감당할 수 있는지도 확인해야 합니다.

적용하기 전에는 캐시가 가능한지, 실제로 효과가 있는지, 유지비용보다 이점이 큰지 순서대로 확인해야 합니다.

세 질문에 답할 수 없다면 일단 캐시부터 붙이기보다 원본 경로와 조회 패턴을 조금 더 살펴보는 편이 낫습니다.
